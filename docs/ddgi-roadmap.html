MiniEngine-DynamicGI

DDGI 구현 로드맵

MiniEngine 에 DDGI (Dynamic Diffuse Global Illumination) 를 구현하기까지의 단계, 결정, 일정, 검증 방법을 정한다. 범위는 Ray Query Infra 부터 DDGI 완료까지다. 이후 단계인 Specular GI (RT Reflection) 는 계획하지 않고, 그 단계가 DDGI 의 산출물을 어떻게 이어받는지만 9장에 적는다.

2목표와 전제

2.1목표

MiniEngine ModelViewer 에 DDGI 기반의 dynamic diffuse GI 를 구현한다. 넓은 world, 빠른 이동, 시간에 따라 바뀌는 조명, 움직이는 물체가 있는 open world action game 에 맞는 형태를 목표로 한다. 무엇이 "맞는 형태" 인지는 3장의 기준으로 판단한다.

2.2전제

발표 일정

매주 금요일에 발표한다 (W2 10/23 ~ W7 11/27). 12/4 (W8) 가 최종 발표다.

사용자가 알려 준 일정

개발 완료

DDGI 와 RT Reflection 의 모든 개발을 11/26 (목) 까지 끝내고 11/27 (W7) 발표에서 보인다. 11/28 ~ 12/3 은 buffer 로 두고 계획된 작업을 넣지 않는다.

사용자 결정

주간 cycle

토요일부터 목요일까지 6일 개발하고, 목요일에 그 주의 개발을 끝낸다. 금요일은 발표와 다음 sprint 계획에 쓴다. 첫 sprint 는 10/19 (월) ~ 10/22 (목) 4일이다.

주말 포함 개발과 발표 전날 개발 마감은 사용자 결정이다. 금요일을 개발 일수에서 뺀 것은 발표 당일에 쓸 수 있는 시간을 알 수 없어 보수적으로 잡은 판단이다.

DDGI 개발 완료

11/12 (목). 11/13 (W5) 발표에서 보인다.

11/26 까지의 개발 가능일 34일 중 RT Reflection 에 W6, W7 sprint 12일을 남긴다. RT Reflection 은 normal/roughness buffer, reflection ray, hit shading 재사용, temporal/spatial denoiser 가 필요해 2 sprint 보다 짧으면 위험하다고 본다.

Ray tracing 방식

inline ray tracing (DXR 1.1 RayQuery) 만 쓴다. DXR 1.0 pipeline (RayGen, shader table) 은 쓰지 않는다.

사용자 결정

개발 GPU

RTX 4060 Laptop. 성능 목표는 이 GPU 기준이다.

개발 PC 에는 RTX 4060 Laptop 과 Intel UHD 가 있고 (2026-10-19 확인), MiniEngine 은 조건을 만족하는 adapter 중 dedicated video memory 가 가장 큰 것을 고른다 (MiniEngine/Core/GraphicsCore.cpp:271-281)

장면 단위

1 m = 100 unit. Sponza 를 100배로 키워 쓴다.

MiniEngine/ModelViewer/ModelViewer.cpp:180

RTXGI 코드 사용

읽기만 하고 복사하지 않는다. 논문과 RTXGI 를 읽고 독립적으로 구현한다.

RTXGI-DDGI 는 NVIDIA RTX SDKs License 이고, SDK 를 open source license 에 종속시키는 사용을 금지한다 (references/RTXGI-DDGI/License.txt 4(e)). 이 repo 는 MIT 다. 법률 검토가 아니라 보수적으로 고른 판단이다.

코드와 asset 으로 확인한 현재 상태 중 계획을 바꾸는 사실만 적는다. 경로는 MiniEngine/ 아래다.

4.1Scene 과 model data

ModelViewer 는 ModelInstance 하나만 둔다. ModelInstance 에는 크기 조절(Resize)만 있고 이동, 회전 setter 가 없다.

ModelViewer/ModelViewer.cpp:72, Model/Model.h:133-175

여러 instance 배치와 움직이는 물체를 위해 추가해야 한다 (M1-7)

화면 그리기용 MeshSorter 는 frustum culling 을 거친 목록이다.

Model/Model.cpp:58

ray 는 화면 밖 물체에도 맞아야 하므로 TLAS 는 Model 전체를 순회해 만든다.

vertex 는 position R32G32B32_FLOAT 가 맨 앞이고, normal, tangent 는 R10G10B10A2_UNORM, UV 는 R16G16_FLOAT 다. Model 의 VB, IB 는 모두 buffer 하나(m_DataBuffer)에 있다.

Model/MeshConvert.cpp:341-363, Model/Model.h:114

BLAS 가 기존 VB 를 복사 없이 입력으로 쓸 수 있다. hit 에서는 normal, UV 를 shader 가 직접 풀어야 한다 (M1-3)

index 는 R16_UINT 이고, 최대 index 가 0xFFFF 를 넘을 때만 R32_UINT 다.

Model/MeshConvert.cpp:144, Model/ModelConvert.cpp:125

geometry desc 와 shader 의 index 읽기가 두 format 을 모두 다뤄야 한다.

vertex 는 node 의 local space 에 있고, world 행렬은 vertex shader 가 곱한다. 변환 때의 localToObject 는 bounds 계산에만 쓰인다.

Model/MeshConvert.cpp:229-256, Model/Shaders/DefaultVS.hlsl:113

TLAS instance transform 에 node 의 world 행렬을 넣는다.

glTF mesh 안의 primitive 는 (psoFlags, 32-bit index 여부, material) 이 같으면 한 Mesh 의 여러 Draw 로 묶인다. Draw 가 여럿인 Mesh 는 VB, depth VB, IB 를 잘못된 위치에 복사한다 (vertex 수와 index 수를 byte offset 자리에 더하고, depth VB 는 같은 위치에 덮어씀).

Model/MeshConvert.h:39-43, Model/ModelConvert.cpp:75-80, :152-155

Sponza 는 해당하지 않는다 (아래 줄). 다른 glTF 를 쓰면 BLAS 입력이 틀린다 (R6)

skinning 은 vertex shader 에서만 한다. skin 된 vertex 가 buffer 로 남지 않는다.

Model/Shaders/DefaultVS.hlsl:88-111

skinned mesh 의 BLAS 는 지금 구조로 만들 수 없다 (D-9)

Sponza (sponza2.gltf): node 381개 (transform 없음), primitive 393개, material 27개 (MASK 3개, double-sided 3개), animation 과 skin 없음. primitive 가 여럿인 glTF mesh 12개는 primitive 마다 material 이 달라서, 위의 묶음 규칙에 따르면 Mesh 393개가 모두 Draw 1개다. MASK material 을 쓰는 primitive 는 32개다.

ModelViewer/Sponza/PBR/sponza2.gltf 를 script 로 집계

정적 장면이다. alpha test 대상은 Mesh 32개다 (M1-8, M4-5)

ModelViewer/ModelViewer.cpp:78-80, :278-283

4.3Core 의 제약

GPU 선택은 inline ray tracing (Tier 1.1, SM 6.5) 을 지원하는 adapter 중 dedicated video memory 가 가장 큰 것을 고른다. SM 6.6 은 검사하지 않는다. ResourceDescriptorHeap[] 방식의 bindless 는 SM 6.6 이 필요하다.

Core/GraphicsCore.cpp:152-164, :266-281

bindless 방식을 정할 때 검사를 6.6 으로 올릴지, SM 6.5 에서 되는 unbounded descriptor table 을 쓸지 같이 정한다 (M1-1)

shader 는 기본 SM 6.2 로 compile 된다. RayQuery 를 쓰는 파일은 파일마다 6.5 이상을 지정해야 한다.

PropertySheets/Desktop.props:18, Model/Model.vcxproj:189

새 ray tracing shader 마다 지정한다.

GpuBuffer 는 COMMON state 로 만들어지고 state 를 추적한다. ComputeContext::SetBufferSRV 는 NON_PIXEL_SHADER_RESOURCE state 를 assert 한다.

Core/GpuBuffer.cpp:34, Core/CommandContext.h:535

AS 는 RAYTRACING_ACCELERATION_STRUCTURE state 에 고정되어야 하므로 기존 buffer 타입과 bind helper 를 쓸 수 없다. 전용 타입을 만든다 (M1-2)

GpuResource::Destroy 는 즉시 해제하고, 지연 해제 장치가 없다.

Core/GpuResource.h:40-45

AS, ray buffer 를 해제하기 전에 GPU 가 끝났음을 보장해야 한다 (M1-2)

RootSignature::Finalize 는 descriptor table 크기를 모두 더하고, DynamicDescriptorHeap::ParseRootSignature 는 그 합이 256 이하인지 assert 한다.

Core/RootSignature.cpp:127-128, Core/DynamicDescriptorHeap.cpp:332-345

큰 bindless table 을 기존 root signature 경로로 만들면 assert 에 걸린다. root signature 를 직접 만들거나 이 계산에서 bindless table 을 빼야 한다.

SetDynamicDescriptor 는 commit 할 때 자기 descriptor heap 을 bind 한다.

Core/DynamicDescriptorHeap.cpp:261, :279

같은 dispatch 에서 s_TextureHeap 의 table 과 섞어 쓸 수 없다. TLAS SRV, 출력 UAV 도 s_TextureHeap 에 둔다.

debug layer 가 INVALID_DESCRIPTOR_HANDLE, DESCRIPTOR_TABLE_NOT_SET 메시지를 숨긴다.

Core/GraphicsCore.cpp:357, :366

bindless 작업 중 binding 오류가 숨을 수 있다. M1 검증 때 한 번은 풀고 확인한다.

ScopedTimer 는 Release 구성에서 아무 일도 하지 않는다.

Core/EngineProfiling.h:34-40

성능 측정은 Profile 구성에서 한다.

debug 용 line, sphere 그리기 기능과 화면 capture 기능이 없다. DirectXTex (dx12 feature) 는 vcpkg 의존성에 있다.

vcpkg.json (repo root)

probe 시각화 (M3-5) 와 HDR capture (M2-4) 를 직접 만든다.

4.4Reference

RTXGI 의 SDK, test harness, 문서 어디에도 inline ray tracing 경로가 없다. probe trace 는 DXR 1.0 RayGen (ProbeTraceRGS.hlsl) 이다.

references/RTXGI-DDGI/samples/test-harness/shaders/ddgi/ProbeTraceRGS.hlsl

trace 는 RayGen 구조를 RayQuery compute shader 로 옮겨 써야 한다.

RTXGI test harness 는 probe ray radiance 를 saturate 해서 저장하고, 설정 파일의 irradiance format 이 unorm (R10G10B10A2_UNORM) 이다.

references/RTXGI-DDGI/samples/test-harness/shaders/ddgi/ProbeTraceRGS.hlsl:200

그대로 따르면 강한 sun 아래의 야외에서 간접광이 잘린다 (D-4)

RTXGI 에는 camera 를 따라가는 cascade 가 없다. 여러 volume 의 blend 와 ray 예산 기반 update 는 UE4 plugin 에 있다.

references/RTXGI-DDGI/ue4-plugin/4.27/RTXGI/Source/RTXGI/Private/DDGIVolumeUpdate.cpp:586-602, :803-823

cascade 는 직접 설계한다 (D-3, M5-4)

5전체 설계

5.1Frame 흐름

  • DDGI update 는 color pass 앞에 둔다. 처음에는 graphics queue 에서 순서대로 실행하고, async compute 는 측정 후 선택 작업으로 둔다 (M5-7).
  • TLAS build 의 정확한 위치(어느 command list, queue)는 M1-1 에서 정한다.

5.2핵심 결정

D-1RTXGI 는 읽기만 하고 독립 구현한다
결정

RTXGI 코드를 복사하지 않고 논문 (Majercik 2019, 2021) 과 RTXGI 를 읽어 독립 구현한다.

근거

license (2.2)

대안

SDK 를 그대로 통합: license 와 DXR 1.0 전제 때문에 제외

D-2Probe trace 는 RayQuery compute shader
결정

thread group 하나가 probe 하나, thread 하나가 ray 하나를 맡는다. ray data 의 규약은 RTXGI 와 같게 한다.

근거

사용자 결정 (inline). RTXGI 의 blend, relocation, classification 이 이 규약을 전제로 한다.

대안

thread 하나가 probe 하나: ray 결과를 blend 가 다시 모아야 해서 이점이 없다

RAY DATA 규약 (ray 하나당 저장하는 값)

misssky radiance거리 1e27
앞면 hitradiance거리 t
뒷면 hitradiance 없음거리 -0.2t
fixed ray거리만, blend 제외32개
D-3Camera 중심 scrolling cascade
결정

volume 은 camera 중심의 scrolling cascade (clipmap) 로 한다. 처음부터 ring buffer indexing 과 cascade 배열로 만들고, M3 에서는 고정된 cascade 1개로 쓴다. 배치는 5.3.

근거

OW1. scroll indexing 을 나중에 모든 shader 에 끼워 넣는 것보다 처음부터 offset 0 으로 두는 편이 싸다.

대안

고정 volume 여러 개 배치: world 크기에 비례해 비용이 늘어 OW1 위반

D-4HDR 을 자르지 않는 format
결정

ray data R32G32B32A32_FLOAT, irradiance R16G16B16A16_FLOAT, distance R16G16_FLOAT, probe data R16G16B16A16_FLOAT 로 시작하고, 압축은 측정 후 한다.

근거

4.4 의 RTXGI saturate 사실. 야외 sun 은 밝다.

대안

RTXGI 기본 (R10G10B10A2_UNORM + gamma 5): memory 는 작지만 HDR 이 잘린다

D-5GI 는 forward pass 에서 적용한다
결정

DefaultPS 의 Diffuse_IBL 이 irradiance cubemap 을 읽는 자리 (DefaultPS.hlsl:208) 를 DDGI sampling 으로 바꾸고, volume 밖에서는 IBL 로 fallback 한다. SSAO 는 DDGI 항에도 계속 곱한다.

근거

G-buffer 가 없다 (4.2). 투명 물체도 같은 경로로 GI 를 받는다. DDGI 는 저주파라 작은 scale 의 가려짐을 AO 로 보완해야 한다 (references/RTXGI-DDGI/docs/Algorithms.md).

대안

G-buffer 를 만들고 screen-space pass 로 적용: RT Reflection 에서 normal buffer 가 필요해지면 다시 검토

DDGI 이후 DefaultPS 의 색 합성

emissive지금과 같음+ sun 직접광다시 켬, M2-1+ DDGI irradiance × SSAOdiffuse IBL 자리, M3-4+ specular IBLRT Reflection 에서 교체
D-6모든 cascade 를 한 Texture2DArray 에
결정

모든 cascade 가 같은 probe 수를 쓰고, 한 Texture2DArray 안에 cascade 별 slice 범위를 둔다. 그러면 cascade 수와 무관하게 SRV 는 irradiance, distance, probe data 3개다. DefaultPS 는 SM 6.2 를 유지하고 common SRV table 로 받는다. 빈 칸이 t18, t19 둘뿐이라 table 을 한 칸 이상 늘린다 (root signature 는 Renderer.cpp:86-97 과 HLSL 문자열 Common.hlsli:22-38 두 곳에 있다).

근거

4.2 의 common SRV table 사실. DefaultPS 의 모든 permutation 을 SM 6.6 으로 올리지 않아도 된다.

대안

DefaultPS 도 SM 6.6 bindless: PSO permutation 전체를 다시 확인해야 한다

D-7Hit 처리를 두 층으로 나눠 공용화
결정

HitSurface (geometry, material 복원) 와 HitLighting (sun + shadow ray, sky, emissive, DDGI 간접광) 을 probe trace, reference path tracer, 이후 RT Reflection 이 같이 쓴다. 구조는 5.4 그림.

근거

WEEK 1 계획에서 RT Reflection 의 hit 간접광을 DDGI 로 채우기로 했다.

대안

사용처마다 따로 구현: 결과가 어긋나 reference 비교가 무의미해진다

D-8광원은 sun, sky, emissive
결정

광원 범위는 sun (directional), sky (IBL cubemap), emissive 다. point, spot light 는 범위 밖이다.

근거

4.2 의 Forward+ 사실. open world 야외 조명은 sun 과 sky 가 지배적이다.

대안

Forward+ light 를 살려 hit 에서도 계산: 일정상 제외

D-9Instance mask 로 물체 범주를 나눈다
결정

TLAS 는 매 frame 갱신하고, instance mask 로 범주를 나눈다. skinned mesh 의 BLAS (compute skinning) 는 만들지 않는다.

근거

OW7. skinning 은 vertex shader 에서만 해서 skin 된 vertex 가 buffer 로 남지 않는다 (4.1).

대안

compute skinning + BLAS refit: 비용과 일정 때문에 제외

INSTANCE 범주

staticGI 에 기여
dynamic rigidGI 에 기여, transform 은 매 frame 갱신
skinnedTLAS 에 없음, 간접광 수신만
debug시각화 전용
D-10Ray 예산 기반 probe update
결정

probe update 는 ray 예산 기반으로 schedule 한다. cascade 별 갱신 주기, round-robin probe window, 새로 들어온 probe 우선.

근거

OW2, OW3. UE4 plugin 의 ray budget 방식을 참고한다.

대안

매 frame 전체 갱신: cascade 가 늘면 예산을 넘는다

D-11Diffuse 만 다루는 reference path tracer
결정

reference path tracer 는 diffuse 만 다루고, probe trace 와 같은 광원 model 과 albedo 처리를 쓴다.

근거

DDGI 가 맡는 것은 diffuse 간접광이다. RTXGI test harness 의 PathTraceRGS.hlsl 도 같은 방식이라 비교가 같은 조건이 된다.

대안

raster 와 같은 BRDF 전체 (WEEK 1 계획): specular 는 RT Reflection 단계에서 확장

D-12Hysteresis 로 조명 변화에 대응
결정

RTXGI 의 irradiance/brightness threshold 방식 (큰 변화에서 hysteresis 를 낮춤) 으로 시작하고, OW4 를 못 맞추면 전역 조명 변화 (sun 각도 변화량) 를 감지해 hysteresis 를 낮추는 규칙을 더한다.

근거

OW4, OW5 는 서로 반대 방향이다. 둘을 같이 측정하며 조정한다.

대안

hysteresis 고정: OW4 를 맞추면 OW5 가 깨진다

5.3Cascade 초기값

M5 에서 쓸 출발점이다. 숫자는 M3 의 측정으로 고친다.

C0C1C2
probe 간격2 m4 m8 m
probe 수24×12×2424×12×2424×12×24
수평 범위±24 m±48 m±96 m
갱신 주기매 frame2 frame4 frame
frame 당 probe6,9123,4561,728
  • probe 당 ray 128개 (그중 fixed ray 32개). RTXGI 기본값 256 의 절반이다. RTXGI 는 64의 배수를 권한다 (references/RTXGI-DDGI/ChangeLog.md:81).
  • texel 수는 RTXGI test harness 설정과 같게 irradiance 8×8, distance 16×16 (각각 border 1 texel 포함) 으로 한다.
  • memory 계산: probe 하나가 irradiance 512 B + distance 1 KiB + probe data 8 B 로 약 1.5 KiB, cascade 하나가 약 10.2 MiB 다. ray buffer 는 volume 전체가 아니라 frame 당 갱신하는 probe 수만큼만 잡는다.

10위험

R1DXR 첫 경험

DX12, DXR 을 처음 다뤄 디버깅 시간이 길어진다.

단계마다 debug view 와 자동 검증을 붙이고, -gpu_debug 1 과 PIX 를 일찍 쓴다.

R2Ray 비용

laptop GPU 에서 incoherent probe ray 비용이 예산을 넘는다.

M3 에서 일찍 측정하고 ray 수, probe 수, 갱신 주기를 조정한다 (D-10).

R3HDR 잘림

HDR 이 잘리는 format, encoding 을 따라 써서 야외 간접광이 틀린다.

D-4

R4장면 단위

장면 단위 때문에 bias, epsilon 이 틀어진다.

값을 unit 이 아니라 m 기준으로 정하고 변환한다 (M4-3).

R5Test 장면의 한계

Sponza 는 open world 가 아니다. 식생, 지형 같은 대표 요소가 부족하다.

M5-1 test layout. 부족한 요소는 측정의 한계로 기록한다.

R6Multi-draw Mesh 버그

다른 glTF 를 쓰면 multi-draw Mesh 버그가 BLAS 입력을 틀리게 만든다.

4.1 의 버그 (MiniEngine/Model/ModelConvert.cpp:152-155) 를 먼저 고친다.

R7Skinned mesh

skinned mesh 는 ray 에 보이지 않는다.

의도한 범위다 (D-9). character 가 만드는 간접 그림자는 없다.

R8일정

sprint 안에 여유일이 없고, 첫 sprint 는 4일뿐이다.

7.2 의 조정 규칙. 그래도 남으면 buffer 주 (11/28 ~ 12/3) 에서 필수 작업만 끝낸다.

R10쉬는 날 없는 6주

주말 없이 6주를 이어서 개발하므로 후반 sprint 의 속도가 계획보다 떨어질 수 있다.

금요일은 개발 일수에 넣지 않았다. 속도가 떨어지면 7.2 의 규칙으로 범위를 줄인다.

R9정적 sky

sky 가 정적 cubemap 이라 time of day 의 sun 과 어긋난다.

처음에는 sky 밝기를 sun 고도에 맞춰 scale 하고, procedural sky 는 선택 작업으로 둔다 (M5-7).
