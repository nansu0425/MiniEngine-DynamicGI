MiniEngine-DynamicGI

DDGI 구현 로드맵

MiniEngine 에 DDGI (Dynamic Diffuse Global Illumination) 를 구현하기까지의 단계, 결정, 일정, 검증 방법을 정한다. 먼저 논문 (Majercik 2019, 2021) 수준의 기본 기능을 정상 동작시키고 검증한다. 그다음 남은 기간에 open world 기준으로 개선 후보의 우선순위를 매겨 순서대로 개선한다. 이후 단계인 RT Reflection 은 계획하지 않고, 이어받는 지점만 9장에 적는다.

1문서 안내

1.1표기

  • 결정, 일정, 목표치, 작업량 추정은 모두 판단이다. 따로 표시하지 않는다.
  • 코드, 문서, spec 으로 확인한 사실은 출처 (파일 경로와 줄 번호) 를 같이 적는다. 줄 번호는 작성 시점 (2026-10-19) 기준이다.
  • 확인하지 않은 추정은 (추측) 으로 표시한다.
  • 설계에 쓴 idea 의 출처를 적는다. 논문은 절 번호로 적고 (예: Majercik 2021 §4.3), RTXGI-DDGI 에서 가져온 idea 는 "idea 출처: RTXGI-DDGI" 로 적는다. RTXGI-DDGI 는 commit f33e496 시점의 idea 만 참고했고 코드는 참고하지 않는다 (D-1).
  • 경로는 repo root 기준이다. references/ 아래 경로는 references/manifest.json 의 commit 기준이다.
  • ID (M1-3, P-2, I5, D-4, OW2, R6) 는 해당 항목으로 가는 link 다. M 은 기본 구현 작업, P 는 개선 단계 작업, I 는 개선 후보, D 는 결정, OW 는 기준, R 은 위험이다.

2목표와 전제

2.1목표

MiniEngine ModelViewer 에 DDGI 기반의 dynamic diffuse GI 를 구현한다. 넓은 world, 빠른 이동, 시간에 따라 바뀌는 조명, 움직이는 물체가 있는 open world action game 에 맞는 형태를 목표로 한다. 무엇이 "맞는 형태" 인지는 3장의 기준으로 판단한다.

2.2전제

진행 방식

1단계에서 논문의 기본 기능을 이 엔진에 구현해 정상 동작시키고 검증한다. 2단계에서 기본 구현을 3장 기준으로 측정하고, 개선 후보에 우선순위를 매겨 순서대로 개선한다.

사용자 결정

기본 기능의 범위

Majercik 2019 의 기능 (probe trace, irradiance 와 distance blend, Chebyshev visibility 를 쓴 sampling, multi-bounce) 과 Majercik 2021 §4 의 품질 개선 (self-shadow bias 와 backface 처리, perceptual encoding, 수렴 heuristic) 이다. Majercik 2021 의 probe 위치 조정 (§5), probe state (§6), tracking window 와 여러 volume (§7) 은 개선 후보다.

범위를 이렇게 나눈 것은 판단이다. RTXGI-DDGI 도 위치 조정, probe state, scrolling 을 기본 설정에서 끈다 (idea 출처: RTXGI-DDGI).

발표 일정

매주 금요일에 발표한다 (W2 10/23 ~ W7 11/27). 12/4 (W8) 가 최종 발표다.

사용자가 알려 준 일정

개발 완료

DDGI 와 RT Reflection 의 모든 개발을 11/26 (목) 까지 끝내고 11/27 (W7) 발표에서 보인다. 11/28 ~ 12/3 은 buffer 로 두고 계획된 작업을 넣지 않는다.

사용자 결정

주간 cycle

토요일부터 목요일까지 6일 개발하고, 목요일에 그 주의 개발을 끝낸다. 금요일은 발표와 다음 sprint 계획에 쓴다. 첫 sprint 는 10/19 (월) ~ 10/22 (목) 4일이다.

주말 포함 개발과 발표 전날 개발 마감은 사용자 결정이다. 금요일을 개발 일수에서 뺀 것은 발표 당일에 쓸 수 있는 시간을 알 수 없어 보수적으로 잡은 판단이다.

DDGI 일수

11/26 까지 개발 가능일 34일 중 DDGI 에 22일을 쓴다. 1단계 기본 구현 16일 (~ 11/5), 2단계 측정과 개선 6일 (11/7 ~ 11/12). RT Reflection 에 W6, W7 sprint 12일을 남긴다.

RT Reflection 은 normal/roughness buffer, reflection ray, hit shading 재사용, temporal/spatial denoiser 가 필요해 2 sprint 보다 짧으면 위험하다고 본다.

Ray tracing 방식

inline ray tracing (DXR 1.1 RayQuery) 만 쓴다. DXR pipeline (RayGen, shader table) 은 쓰지 않는다.

사용자 결정

개발 GPU

RTX 4060 Laptop. 성능 목표는 이 GPU 기준이다.

개발 PC 에는 RTX 4060 Laptop 과 Intel UHD 가 있고 (2026-10-19 확인), MiniEngine 은 조건을 만족하는 adapter 중 dedicated video memory 가 가장 큰 것을 고른다 (MiniEngine/Core/GraphicsCore.cpp:271-281)

장면 단위

1 m = 100 unit.

glTF 2.0 의 길이 단위는 m 이고, ModelViewer 는 Sponza 를 100배로 키운다 (MiniEngine/ModelViewer/ModelViewer.cpp:180). Sponza 의 POSITION 범위 37.2 × 15.6 × 22.9 도 m 로 보면 자연스럽다.

RTXGI-DDGI 참고 범위

idea 만 참고하고 코드는 참고하지 않는다. references/ 에도 두지 않는다 (README 의 참고 범위).

RTXGI-DDGI 는 NVIDIA RTX SDKs License 이고, SDK 의 복사, 수정, 파생물 작성을 막으며 SDK 를 open source license 에 종속시키는 사용을 금지한다 (License.txt 4(b), 4(e)). 이 repo 는 MIT 로 공개되어 있다. 법률 검토가 아니라 보수적으로 고른 판단이다.

10위험

R1DXR 첫 경험

DX12, DXR 을 처음 다뤄 디버깅 시간이 길어진다.

단계마다 debug view 와 자동 검증을 붙이고, -debug 1 -gpu_debug 1 과 PIX 를 일찍 쓴다.

R2Ray 비용

기본 volume 은 frame 당 약 273만 ray 다 (5.3). laptop GPU 에서 예산을 크게 넘을 수 있다.

M3-2 의 trace timer 로 W4 초에 잰다. 기본 구현이 진행되지 않을 만큼 느리면 ray 수를 줄이고, 예산 맞추기는 개선 후보 (I10, I11) 로 다룬다.

R3HDR 잘림

HDR 이 잘리는 format, encoding 을 따라 써서 야외 간접광이 틀린다.

D-4

R4장면 단위

m 단위를 전제로 한 길이 값을 그대로 쓰면 bias, 거리 상한, distance 정밀도가 틀어진다.

길이 parameter 는 probe 간격 기준으로 정하고 (M3-1), distance 는 R32G32_FLOAT 로 둔다 (D-4).

R5Test 장면의 한계

Sponza 는 open world 가 아니다. 식생, 지형 같은 대표 요소가 부족하다.

넓은 범위가 필요하면 P-4 의 layout 을 쓴다. 부족한 요소는 측정의 한계로 기록한다.

R6Multi-draw Mesh 버그

다른 glTF 를 쓰면 multi-draw Mesh 버그가 BLAS 입력을 틀리게 만든다.

M1-1 의 지원 범위에서 assert 로 막고, 다른 glTF 를 쓰기 전에 4.1 의 버그 (MiniEngine/Model/ModelConvert.cpp:152-155) 를 고친다.

R7Skinned mesh

skinned mesh 는 probe ray 와 reflection ray 에 보이지 않는다.

의도한 범위다 (D-9). 수신 쪽 문제는 I8, I13 후보로 다룬다.

R81단계 일정

1단계 필수 작업이 가용일보다 많을 수 있고, 첫 sprint 는 4일뿐이다.

7.2 의 조정 규칙. 그래도 남으면 buffer 주 (11/28 ~ 12/3) 에서 필수 작업만 끝낸다.

R9정적 sky

sky 가 정적 cubemap 이라 time of day 의 sun 과 어긋난다.

개선 후보 I14

R10쉬는 날 없는 6주

주말 없이 6주를 이어서 개발하므로 후반 sprint 의 속도가 계획보다 떨어질 수 있다.

금요일은 개발 일수에 넣지 않았다. 속도가 떨어지면 7.2 의 규칙으로 범위를 줄인다.
